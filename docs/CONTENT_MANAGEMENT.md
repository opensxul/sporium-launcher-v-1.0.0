# Instance content management — v3.0 phase 10, complete

Tracked Modrinth content and locally imported/adopted JARs support single/bulk enable, disable and confirmed delete. Toggles apply to mods; tracked resource packs and shaders can be deleted. Installation supports the existing contextual Modrinth dialog and a local file picker/drop preview. Files placed manually in instance folders appear in a separate inventory and are never adopted into managed receipts automatically. **Manage file** offers an explicit adoption preview.

Select individual rows or all visible rows (search/type filters apply). Bulk actions use all explicitly selected rows, including selections outside the current filter; the confirmation lists the exact affected items. Enable/disable skip items already in the requested state. Confirmation warns that other mods may require selected files. This is intentional for diagnosis; the launcher does not claim that arbitrary disabled-mod combinations will launch.

Disabled JARs reside in `mods_disabled`, with the same source, project/version/file IDs, hashes and dependency metadata. The receipt retains one entry for each file; it cannot contain active and disabled copies of the same mod filename. Unknown destination files, modified/missing sources, stale selections and active instance leases block changes. No automatic file adoption or overwrite occurs.

Each batch validates all selected files before making changes. `.sporium/content-change.json` records the before/after receipt and selected files. Files are copied through flushed temporary files and published without clobbering; only verified sources are removed. Recovery validates the journal and rolls forward under the exclusive instance lease before content reads or game launch. A crash between publishing and removing a source cannot leave two active files at the next launcher-controlled game start. Conflicts retain the journal and files for diagnosis. Deletes first move files to private transaction trash, commit the receipt/history and then clean up. An interrupted cleanup can leave harmless private trash; this is not a user restore-point feature.

`.sporium/content-history.json` contains recent add/enable/disable/delete operations, retained across restart with idempotent transaction IDs. History is bounded to 500 entries and 8 MB; titles are limited to 160 characters. Pre-existing installs are not fabricated as historical events. File paths are behind Details in the installed list, installation plan and transfer view.

Current tests cover bulk round-trip with provenance, deletion preserving local files, changed source/stale request/destination collision, active-instance exclusion and partial-publication recovery before reads/launch. The extended Modrinth native scenario also exercises UI selection, cancelled confirmation, bulk disable, restart, re-enable, single deletion and history using real installed files in `.local` only.

## Later phases and supported limits

- Unpacked resource/shader folders remain read-only. A mod ID alone never identifies a Modrinth project; provider assistance requires verified exact artifact matching as described below.
- Restore-point browsing/rollback and background/automatic update policies are phase 12. Manual compatible updates and pin/ignore controls are implemented below.

Full server profiles and plugin installation remain phase 13; full pack import/export is phase 11.

## Compatible Modrinth updates

**Check for updates** opens an instance dialog. Per-row and selected-row actions seed its selection; **Select all available updates** includes all eligible tracked projects. Imported local files have a separate local status and cannot enter a provider update. Checks release the instance read lease before contacting the provider, so provider outages do not prevent local play. Closing a check dismisses its UI. The official [project version API](https://docs.modrinth.com/api/operations/getprojectversions/) supplies exact Minecraft/loader/environment metadata, dependency version IDs, files and hashes.

Only later dated, listed, compatible releases are offered. Stable installed content uses stable releases; beta/alpha content may use its channel or a more stable one. The instance's Minecraft version and loader never change. States include current, available, pinned, ignored, incompatible, local and unavailable. A per-project pin and ignored exact version ID persist separately from content receipts. A newer version is not suppressed by an older ignored ID.

Preview is read-only. A multi-root resolver checks required dependency changes and exact requirements of retained projects before producing the plan. Pin/ignore protects dependencies too. Existing disabled dependencies are not silently enabled to satisfy active projects. Updating a disabled selected mod retains `mods_disabled`. Unchanged dependency files stay out of the replacement set. Plans expire after 15 minutes, bind to the receipt bytes and recheck source hashes, destinations and policies before applying.

All artifacts are downloaded and verified before mutation. Unknown destination files, modified/missing managed files, stale plans, dependency conflicts and active game leases block replacement. Before publishing `.sporium/content-update.json`, the launcher saves all previous managed files, instance/provenance metadata and relevant settings (`config`, `options*.txt`, `servers.dat`) under `.sporium/content-snapshots/<transaction>`. Settings backup is limited to 4096 entries, 32 MB per file and 128 MB total; linked paths are rejected. Worlds and arbitrary unmanaged content are left in place. Snapshot manifests and saved file hashes are validated during recovery. This supplies restoration data; there is no rollback UI or automatic pruning yet.

The update journal records complete before/after receipts, exact replacements and a stable history event. Recovery validates the entire transaction, frozen staged artifacts and old snapshot bytes before removing/publishing files. It rolls forward under the exclusive instance lease before content reads or game launch, including same-filename replacements and interrupted partial publication. Receipt, snapshot history and old → new update history are idempotent. Interrupted downloads/cancel leave the old installed state unchanged; publication completes through the journal rather than being cancelled midway.

Core tests cover stable/exact compatibility, pin/ignore persistence, pinned dependency refusal, retained exact requirements, disabled state, preserved local/world/config bytes, corrupt staging, same-name replacement, changed files, unknown destinations, stale policies, active leases, interrupted batch recovery and a 100-project update-all plan. Verification on 2026-10-01: 80 offline Rust tests and strict Clippy passed. `npm.cmd run test:update-native` passed 8 real Windows/live CDN checks, including actual updated Fabric renderer/audio launch. Its isolated evidence is `.local/content-update-smoke/result.json`; viewport screenshots at 1400/1000 were reviewed. The final rebuilt executable passed all 15 baseline native checks; all test processes were closed.

## Local JAR imports and manual inventory

Inside an instance, **Добавить из файла / Add from file** opens the Windows multi-file picker. JARs may also be dropped into the installed-content section. A preview names the destination instance and lists detected mod IDs, loader, version and dependencies under Details. Source files remain untouched. Private staging freezes the selected bytes, and SHA-1/SHA-512 checks run again before committing through the existing install journal. Cancel removes only that preview's staging.

The metadata reader examines bounded ZIP metadata without extracting or executing the JAR. It recognizes Fabric `fabric.mod.json`, Forge/NeoForge TOML metadata and legacy `mcmod.info`; it rejects understood incompatible game/loader requirements, Fabric server-only mods, corrupt archives and duplicate known mod IDs across active/disabled folders and the selected batch. Numeric ranges are checked conservatively. Unsupported version syntax, dependency findings, nested mods and unknown metadata require an explicit **Install anyway** action. Dependencies from local files are inspected as described below but not automatically downloaded. This is not a claim that any arbitrary local mod combination will launch.

Limits: 64 selected files, 200 MB per JAR and 1 GB per batch; bounded metadata reads, no linked/junction paths, preview lifetime 15 minutes. Receipt schema 2 preserves local metadata alongside existing Modrinth entries; schema 1 remains readable. Imported files participate in the same toggle/delete/history mechanism.

**Added manually** scans `mods`, `mods_disabled`, `resourcepacks` and `shaderpacks` without rewriting files or receipts. Recognized JAR metadata is displayed; incompatible or unreadable metadata gets a separate status. ZIP/unpacked resource packs and shader packs have unknown compatibility. Refresh rescans the instance folders. Original filenames/paths stay under Details. Unmanaged files cannot be toggled or deleted until explicit adoption; unpacked folders remain read-only.

## Explicit adoption, hash matching and local icons

**Управлять файлом / Manage file** previews one manually placed JAR or ZIP in the selected instance. The default operation is entirely local. Known incompatible or corrupt JARs, duplicate known mod IDs, active/disabled filename collisions, linked paths and the exact Sporium-owned skin helper cannot be adopted. ZIP packs retain unverified local metadata; warnings require a checked confirmation. Cancel never modifies user files or receipts. Individual archives are bounded to 200 MB.

**Распознать в Modrinth / Identify on Modrinth** is optional. The official [version-from-hash API](https://docs.modrinth.com/api/operations/versionfromhash/) is queried with SHA512. A match must also agree on SHA1 and size, an approved CDN artifact, concrete project type and exact game/loader/environment compatibility. Source/development/signature artifacts are refused. Original filenames, including user renames, remain unchanged; official version/file metadata and source IDs are preserved. Provider failure or no match remains explicitly local with a warning, never a guessed project association. The user confirms the proposed identity before its receipt is saved. Matched files participate in the existing update/pin/ignore system; local files do not.

Previews expire after 15 minutes and bind to both instance context and current receipt. Confirmation rechecks current metadata, duplicates and file hashes. `.sporium/content-adoption.json` journals the previous receipt, adopted record and history event. Recovery adds only metadata, never moves/replaces a game file, and is idempotent before content reads or launch. Changed files or conflicting receipts retain the journal for diagnosis. The exact launcher-owned skin helper is also rejected by direct IPC, regardless of UI state.

Local icons use a separate read-only IPC. Fabric icon paths/resolution maps, Forge/NeoForge `logoFile`, legacy `mcmod.info` and `pack.png` are read inside archives without extraction or execution. Only bounded PNG payloads (128 KiB; dimensions at most 1024×1024) become data URLs. Metadata, entry counts and archive size are bounded; path traversal and duplicate selected entries are rejected. Unsupported or broken icons fall back to the existing content-type glyph. Managed icon reads bind to the receipt hash; refreshed manual-file icons use a new cache key. PNG/base64 is not persisted in receipts.

Core tests cover cancellation/unchanged bytes, explicit warnings, unavailable provider, hashes/size/URL/compatibility refusal, renamed exact matches, stale context/receipts, active leases, duplicate IDs, corrupt files, disabled adoption, ZIP management, crash recovery and bounded icon reads. Native scenario: `npm.cmd run test:adoption-native`, with a fresh isolated `.local/content-adoption-smoke/run-*/data` library, local archive fixtures and a read-only copy of a previous isolated AppleSkin artifact. It verifies UI adoption/cancel/warnings/icons, toggle and restart, delete/history, preserved worlds/local notes, live SHA512 matching and subsequent update eligibility. It does not repeat native picker/drop automation or claim a new Minecraft launch.

Final verification for this increment, 2026-10-01: 89 offline Rust tests, strict all-targets Clippy, generated bindings, 8 frontend tests, 4 browser tests, ESLint/Prettier and embedded build pass. Final executable passed all 8 adoption checks (including local dependency details after a live match) and all 15 baseline native checks. Evidence: `.local/content-adoption-smoke/result.json`; reviewed screenshots at 1400/1000 widths. Test processes closed; normal user library untouched.

Verification after source recovery: Rust tests cover mixed receipts, frozen staged bytes, source preservation, explicit unknown acceptance/cancel, incompatibility, duplicate IDs, numeric ranges and read-only manual indexing. The Windows picker/import UI was manually confirmed by the user. Native automated checks exercise real IPC; they do not claim OS drag/drop or native picker automation.

## Offline local dependency diagnostics

**Проверить зависимости / Check dependencies** opens a read-only report inside an instance. It inspects the actual JARs in `mods` and `mods_disabled`, including manual and provider-managed files. The default filter shows findings; it can reveal satisfied requirements and optional suggestions. Disabled owners are labelled, with their requirements excluded from active error totals. Refresh rescans metadata without modifying files, receipts or history. Paths and version predicates are under Details.

The graph records each mod's actual embedded version, including individual IDs in multi-mod Forge/NeoForge JARs. Fabric aliases do not inherit an invented version. Built-in Minecraft/selected loader requirements use the instance context; Java runtime requirements remain explicitly unconfirmed. Required dependencies distinguish missing, disabled, version mismatch, satisfied and unknown. Declared hard incompatibilities and softer discouraged combinations have separate severities. Optional Fabric suggestions never become mandatory; an installed optional Maven dependency still checks its declared version range. Server-only dependency declarations are excluded from the client report; unknown sides/types remain uncertain.

Predicate handling follows the declared metadata dialect: Fabric arrays are OR, whitespace terms are AND; numeric comparisons, wildcard, caret and tilde are supported, ignoring build suffixes. Maven checks numeric bracket intervals. Qualified/prerelease ordering, bare Maven recommendations, custom syntax and manifest substitutions remain unknown. References: [Fabric metadata specification](https://wiki.fabricmc.net/documentation:fabric_mod_json_spec), [Forge mod metadata](https://docs.minecraftforge.net/en/1.20.1/gettingstarted/modfiles/), [NeoForge mod metadata](https://docs.neoforged.net/docs/gettingstarted/modfiles/). This is bounded metadata inspection, not execution of the loader's full resolver or a guarantee of gameplay compatibility.

Active unrecognized, incompatible, corrupt or nested archives make the inventory incomplete. Unresolved providers then get an unknown verdict instead of a definite missing/disabled claim. Duplicate active primary mod IDs are flagged; conflicting provider versions are not guessed. Nested JARs are not extracted or recursively executed. Limits include 4096 directory entries, existing per-archive metadata limits, 16384 dependency edges and a 12 MB report. Old local receipts without the new version/dependency arrays remain readable; diagnostics always use fresh archive metadata.

Local import previews check the selected batch together with installed files. Adoption previews show findings for the selected existing mod. Both warn explicitly and bind the diagnostic report to confirmation; changed graph or instance/loader context requires a fresh preview before any commit. Adoption still preserves bytes and original source rules. A missing or unknown required mod ID can open the existing contextual Modrinth browser with a search term, retaining Minecraft/loader filters. This never associates a mod ID with a project automatically or installs anything without user selection and the normal reviewed plan.

`npm.cmd run test:diagnostics-native` uses a fresh isolated `.local/content-diagnostics-smoke/run-*/data` library and bounded local ZIP fixtures. It covers displayed findings/filters, contextual search, adoption warnings, read-only refresh, incomplete inventories, staged batch checks, stale confirmation and restart/world preservation. Native picker/drop and game launch are not repeated in this increment.

Final verification on 2026-10-01: 97 offline Rust tests (70 unit + 27 integration), strict all-targets Clippy, current generated bindings, 8 frontend tests, 4 browser tests, ESLint/Prettier and embedded desktop build pass. Final executable passed 7 diagnostic native checks, all 8 adoption checks including live official recognition, and all 15 baseline native checks sequentially. `.local/content-diagnostics-smoke/result.json` contains current evidence; 1400/1000 screenshots were reviewed without horizontal overflow. All fixture processes closed; normal user data untouched.

## Required dependencies for exact matched local mods

Local import offers **Распознать и найти зависимости / Identify and find dependencies**. The official SHA512 lookup must also prove SHA1, artifact size, project/version identity, safe CDN file and compatible game/loader/client environment. Required provider dependencies are resolved without guessing project IDs from names. Optional dependencies are not downloaded; existing incompatible or disabled dependencies are not silently replaced/enabled. Up to 16 roots may request provider assistance; ordinary local import retains its 64-file limit.

The enriched preview stages verified dependency bytes privately, retains each selected root's original filename and bytes, and checks embedded metadata for the combined batch against the actual existing graph. Known blocking selected-file findings refuse publication. Provider errors leave the ordinary local preview usable. No receipt changes occur until explicit confirmation; cancellation removes only staging. A confirmed recognized import saves official provenance and update eligibility. Already managed local mods offer **Установить зависимости / Install dependencies**: recognition verifies identity for the plan, while the original root stays local. Its required dependencies use the common download/progress/cancel/install journal. Fresh root hashes, instance, receipt and graph are rechecked before download and publication.

## Maps, worlds and datapacks

Instance content includes **Миры / Worlds** and **Добавить карту или датапак / Add map or datapack**. A local Java world ZIP must contain exactly one nonempty `level.dat`, at its root or under one unambiguous wrapper directory. The launcher freezes the archive and extracts into private staging, then previews title, source and file count. Compatibility is explicitly unconfirmed; a checked acceptance is required. Import creates a fresh `saves/Sporium-<UUID>` world without overwriting existing worlds. Display titles, import source/hash/time and idempotent history persist. The world publication journal verifies the entire extracted tree and recovers on either side of the atomic directory rename before reads/launch. No world-delete action is added.

Local datapacks require an explicitly chosen real world and a root `pack.mcmeta` plus `data/` content. Bounded positive pack format values or ordered major/minor format ranges are validated structurally; exact Minecraft compatibility is not guessed. ZIP bytes are kept intact under `saves/<world>/datapacks`. The selected world's `level.dat` hash is checked again after preview; a missing or changed world blocks installation. The record participates in the normal installed list, source/details, delete and history; deletion removes only its verified ZIP. Activation is controlled inside Minecraft.

The contextual Modrinth catalog has a **Датапаки / Datapacks** tab. Modrinth v2 may classify the project as `mod`; installation checks the concrete version's `datapack` loader and exact Minecraft version. Datapacks may correctly declare server-only environment because singleplayer uses an integrated server. The world selector has no automatic default. Required datapack dependencies use that same world; declared required resource packs use `resourcepacks`. Required resource-pack artifacts attached to a version are retained. The normal verified download/progress/cancel journal is reused and does not require installing Java merely to copy a datapack. Managed datapacks join compatible updates and project-level pin/ignore; updates preserve all recorded world destinations for that project. World names appear in primary rows and confirmation, with paths under Details.

Archive limits: 500 MB compressed/per file, 2 GB expanded total, 10000 entries, bounded metadata and 15-minute previews. Absolute/traversal/Windows-device/ADS paths, links, ambiguous roots, case-insensitive collisions, corrupt payloads and changed staging trees are refused. Unpacked external worlds are discovered for explicit destination selection; importing arbitrary launcher directories and complete packs remains phase 11.

`npm.cmd run test:world-native` uses fresh `.local/world-content-smoke/run-*/data` libraries. Native IPC checks local archive review/acceptance/cancel, while UI checks world selection, displayed provenance, contextual provider installation, managed dependency confirmation and layout/restart. OS picker/drop automation is not claimed or repeated. Synthetic `level.dat` fixtures verify byte preservation and publication, not Minecraft world playability. Live provider checks use real Mod Menu and Terralith artifacts.
